# 惠搭 HuiDa 消费优惠资源撮合平台 PRD（MVP 精简版）

> 本文档为 `sdp/PRD101.md` 的精简版，**删除所有可选项（P1/P2）内容，仅保留 MVP 最小可落地方案（全部为 P0 必做项）**。依据需求规范 `tpl/prd_rules.md` 编写。

---

## 1. 项目概述

### 1.1 项目背景

日常生活中，不同用户之间存在消费优惠资源的不平衡：

- **资源闲置**：一部分用户拥有优惠券、会员权益、团购资格等优惠资源，但无法充分利用。
- **需求缺口**：另一部分用户有真实消费需求，却缺少优惠资源，只能以原价消费。
- **信息差**：供需双方彼此不认识、缺乏可信的对接渠道。

惠搭 HuiDa 通过互联网平台撮合供需双方：让拥有优惠资源的用户（B）在**符合相关平台规则**的前提下，为有消费需求的用户（A）提供代下单、代购等合规服务，帮助 A 降低消费成本、帮助 B 让闲置优惠资源产生收益。

**产品 Slogan**：让优惠找到需要它的人。

### 1.2 项目目标

**MVP 核心目标**：跑通「发布 — 撮合 — 交易 — 履约 — 评价」核心闭环，验证模式可用。

| 层级 | 目标 | 衡量指标（示例） |
|---|---|---|
| MVP 目标 | 核心交易闭环可用 | 核心流程完成率、首单转化时长 |
| 用户目标（A） | 以更低成本完成消费 | 平均节省金额、需求满足率 |
| 用户目标（B） | 让闲置优惠资源合规变现 | 接单量、履约完成率 |

### 1.3 项目范围

**MVP 范围内（全部为 P0）：**

- 用户注册登录、实名认证、A/B 双身份切换与钱包账户。
- 需求方（A）发布与管理消费需求。
- 资源方（B）发布与管理优惠资源、接单报价。
- 供需撮合：搜索、分类浏览、规则匹配、匹配通知、详情页。
- 站内沟通与价格/服务费协商。
- 担保交易（资金托管）、下单、支付、履约凭证、确认、结算。
- 交易评价与信用分。
- 纠纷申诉、客服介入与退款。
- 合规审核与交易风控。
- 站内消息通知。
- 平台运营后台（内容审核、订单资金、纠纷、用户信用）。

**关键约束：**

1. 优惠资源的使用必须符合**原发放平台规则与相关法律法规**，禁止违规倒卖、套现。
2. B 提供的是「服务」（代下单/代购等），不一定涉及优惠券所有权转让。
3. 资金采用平台担保托管，确认履约后再结算给 B，保障双方权益。

## 2. 用户角色定义

平台采用「同一账户、多重身份」设计：一个注册用户可同时具备需求方（A）与资源方（B）身份；未完成实名认证的用户仅可浏览，认证后方可发布与交易。

| 角色编号 | 角色名称 | 定位 | 主要权限 |
|---|---|---|---|
| R-A | 需求方 A | 有消费需求、缺少优惠的用户 | 发布需求、筛选资源、下单支付、确认履约、评价、申诉 |
| R-B | 资源方 B | 拥有优惠资源、提供合规服务的用户 | 发布资源、接单报价、协商、履约服务、收款、评价、申诉 |
| R-OP | 平台运营 | 内容审核与交易秩序维护 | 内容审核、订单与资金管理、用户与信用管理 |
| R-CS | 客服 | 纠纷与咨询处理 | 查看订单、介入纠纷、发起退款 |
| R-RISK | 风控/审核 | 合规与风险控制 | 违规识别、交易拦截、账户处置 |

## 4. 业务流程

### 4.1 核心交易主流程

平台存在两条互为补充的撮合路径：**需求驱动**（A 先发需求，B 应答）与**资源驱动**（B 先发资源，A 直接下单）。两者在「创建订单」后汇入同一套交易与履约主流程。

```mermaid
flowchart TD
    Start([用户登录并实名认证]) --> Role{发起方}
    Role -->|需求方 A| A1[发布消费需求]
    Role -->|资源方 B| B1[发布优惠资源]
    A1 --> Match[平台撮合/搜索/匹配]
    B1 --> Match
    Match --> Chat[双方沟通与报价协商]
    Chat --> Agree{达成价格/服务费一致?}
    Agree -->|否| Chat
    Agree -->|是| Order[创建订单]
    Order --> Pay[A 担保支付→资金托管冻结]
    Pay --> Fulfill[B 履约：代下单/代购并上传凭证]
    Fulfill --> Verify{A 核验凭证}
    Verify -->|一致| Confirm[确认完成]
    Verify -->|异议| Dispute[发起纠纷申诉]
    Confirm --> Settle[平台结算款项至 B 钱包]
    Settle --> Rate[双方互评→更新信用分]
    Rate --> End([交易完成])
    Dispute --> CS[客服介入裁决]
    CS --> Refund[退款/部分退款/正常结算]
    Refund --> End
```

**主流程步骤说明：**

| 步骤 | 角色 | 操作 | 关联需求 |
|---|---|---|---|
| 1 | A / B | 登录、实名认证、（B）完成资质声明 | FR-USER-01/03/05 |
| 2 | A | 发布消费需求（或浏览资源直接下单） | FR-DEM-01/05 |
| 2' | B | 发布优惠资源（或在接单大厅应答需求） | FR-RES-01/05 |
| 3 | 平台 | 撮合、搜索、匹配并通知匹配结果 | FR-MATCH-01/02/03/05 |
| 4 | A & B | 站内沟通，就价格与服务费协商一致 | FR-CHAT-01/02、FR-RES-06 |
| 5 | 平台 | 创建订单，明确金额构成与履约方式 | FR-TRADE-01/04 |
| 6 | A | 担保支付，款项进入平台托管账户冻结 | FR-TRADE-02/03 |
| 7 | B | 履约（代下单/代购）并上传凭证 | FR-FULFILL-01 |
| 8 | A | 核验凭证，确认完成或发起异议 | FR-FULFILL-02 |
| 9 | 平台 | 确认后将款项结算至 B 钱包 | FR-TRADE-06 |
| 10 | A & B | 互评并更新信用分 | FR-CREDIT-01/02 |

### 4.2 需求驱动流程（A 发需求 → B 应答）

```mermaid
flowchart LR
    A1[A 发布需求] --> A2[进入接单大厅/匹配队列]
    A2 --> B2[B 浏览并报价应答]
    B2 --> A3[A 查看多个报价与 B 信用]
    A3 --> A4[A 选定 B 或继续议价]
    A4 --> Order[创建订单]
```

- A 发布需求后，系统按场景/平台/门店/价格/时效进行规则匹配并推送给合适的 B。
- 多个 B 可分别报价，A 依据报价、信用分、历史评价择优选定。
- 选定后进入主流程的「创建订单」环节。

### 4.3 资源驱动流程（B 发资源 → A 直接下单）

```mermaid
flowchart LR
    B1[B 发布优惠资源] --> S[搜索/分类曝光]
    S --> A5[A 浏览资源详情]
    A5 --> A6{需要议价?}
    A6 -->|是| Chat2[沟通协商]
    A6 -->|否| Order2[直接下单]
    Chat2 --> Order2
    Order2 --> Pay2[担保支付]
```

- A 可直接从资源详情页发起下单，价格明确时可跳过议价直接进入支付。
- 若资源需按具体需求定制（如指定门店/商品），则先沟通协商再下单。

### 4.4 纠纷与退款流程

```mermaid
flowchart TD
    D0[履约或确认阶段产生争议] --> D1[一方发起申诉并提交证据]
    D1 --> D2{双方能否自行协商?}
    D2 -->|能| D3[协商一致→撤单/退款/继续履约]
    D2 -->|不能| D4[客服介入]
    D4 --> D5[核验订单/会话/凭证]
    D5 --> D6{裁决结果}
    D6 -->|全额退款| R1[托管资金原路退回 A]
    D6 -->|部分退款| R2[按比例分配给 A 与 B]
    D6 -->|申诉不成立| R3[正常结算至 B]
    R1 --> D7[更新订单与钱包、记录信用]
    R2 --> D7
    R3 --> D7
    D7 --> D8{是否违规?}
    D8 -->|是| D9[警告/限权/封禁/黑名单]
    D8 -->|否| D10([纠纷结束])
    D9 --> D10
```

- 客服裁决基于订单信息、协商留痕与履约凭证，确保客观公正。
- 退款资金流向同步更新订单状态与双方钱包，并计入信用记录。
- 对确认违规的账户执行相应处置。

### 4.5 订单状态流转

```mermaid
stateDiagram-v2
    [*] --> 待支付: 创建订单
    待支付 --> 已取消: 超时/主动取消
    待支付 --> 待履约: A 担保支付成功
    待履约 --> 履约中: B 开始代下单/代购
    履约中 --> 待确认: B 上传履约凭证
    待确认 --> 已完成: A 确认/超时自动确认
    待确认 --> 纠纷中: A 发起异议
    履约中 --> 纠纷中: 任一方申诉
    纠纷中 --> 已完成: 裁决结算给 B
    纠纷中 --> 已退款: 裁决全额/部分退款
    已完成 --> [*]
    已退款 --> [*]
    已取消 --> [*]
```

| 订单状态 | 含义 | 触发动作 |
|---|---|---|
| 待支付 | 订单已创建，等待 A 支付 | 创建订单 |
| 待履约 | 款项已托管，等待 B 服务 | A 支付成功 |
| 履约中 | B 正在代下单/代购 | B 开始履约 |
| 待确认 | B 已提交凭证，等待 A 核验 | B 上传凭证 |
| 已完成 | 交易成功，款项已结算给 B | A 确认 / 超时自动确认 |
| 纠纷中 | 存在争议，客服介入处理 | 一方发起申诉 |
| 已退款 | 依裁决完成退款 | 客服裁决退款 |
| 已取消 | 订单取消（未支付或协商取消） | 超时 / 主动取消 |

### 4.6 关键业务规则

1. **合规优先**：B 提供的是合规「服务」，优惠资源的使用必须符合原发放平台规则与法律法规，禁止套现、倒卖等违规行为（FR-RES-02、FR-RISK-01/02）。
2. **担保交易**：A 支付的款项由平台托管，确认履约后方结算给 B，避免「先款后货」风险（FR-TRADE-02/06）。
3. **协商留痕**：价格、服务方式、时效等关键协商内容须在平台内留痕，作为履约与纠纷裁决依据（FR-CHAT-02）。
4. **信用驱动**：信用分影响撮合排序与曝光权重，形成正向激励（FR-CREDIT-02/03）。
